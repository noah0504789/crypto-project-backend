# 다중 범위 요청 오케스트레이션

여러 범위에 걸친 요청을 **조사(병렬) → 종합 → 계획 → 실행(순차) → 검증(병렬)** 순서로 처리한다. 조사는 서브에이전트가 각자 컨텍스트에서 하고, 메인은 결론만 받아 흐름을 관리한다.

## 언제 쓰나

| 쓴다 | 안 쓴다 |
|---|---|
| 2개 이상 모듈에 걸침 | 파일 1~2개 수정 |
| 외부 계약(proto/Kafka/Redis/STOMP/JWT/REST/DB)이 걸림 | 오타·주석 수정 |
| backend 외 저장소(frontend/infra)가 걸림 | 이미 위치를 아는 단일 버그 수정 |
| 기능 + 테스트 + CI/CD를 같이 봐야 함 | 단순 조회 질문 |

## 1단계 — 요청 분해

먼저 요청을 축으로 쪼개고 **어느 축이 켜졌는지 명시**한다. 여기서 축을 빠뜨리면 뒤가 전부 어긋난다.

| 축 | 켜지는 신호 |
|---|---|
| 코드 위치·흐름 | "어디 있어", "어떻게 동작해", 새 기능 추가 |
| 외부 계약 | proto·topic·Redis key·STOMP destination·JWT claim·REST 경로·DB schema 언급 |
| 프론트 | 화면·요청/응답 형태·로그인·실시간 수신 언급, 또는 계약 축이 켜짐 |
| 인프라·배포 | 새 서비스 추가, 포트·health check·환경변수·컨테이너·배포 전략 언급 |
| 검증 | 코드를 실제로 바꾸는 모든 요청 |

## 2단계 — 병렬 조사 (한 번에 흩뿌린다)

켜진 축에만 에이전트를 붙인다. **순차로 하나씩 부르지 않는다 — 한 응답에서 전부 호출한다.**

| 축 | 에이전트 | 저장소 | 프롬프트에 반드시 넣을 것 |
|---|---|---|---|
| 코드 위치·흐름 | `module-explorer` | backend | 모듈명. 모듈이 여러 개면 **모듈마다 따로 호출** |
| 외부 계약 | `contract-scanner` | backend | 계약 유형 + 현재 값 + 바꾸려는 값 |
| 프론트 | `frontend-explorer` | frontend | 화면/기능명, 확인할 API 경로 |
| 인프라·배포 | `deploy-auditor` | infra | 대상 서비스명, 배포 전략 |
| 스택 현재 상태 | `stack-inspector` | infra | 확인할 컨테이너/포트 (실행 중인 스택 점검이 필요할 때만) |

병렬 호출 규칙:
- 모듈이 3개면 `module-explorer`를 3번 호출한다(모듈당 1개). 한 에이전트에 3개를 몰면 컨텍스트 격리 이점이 사라진다.
- 계약 유형이 여러 개면(proto + Kafka + Redis) `contract-scanner`도 유형별로 나눈다.
- 서로 다른 저장소의 에이전트는 항상 동시에 부를 수 있다 — 의존이 없다.

**의존이 있는 경우만 순차로 한다**: 계약의 현재 값을 모르면 `module-explorer`로 먼저 찾고, 그 값을 `contract-scanner`에 넘긴다.

## 3단계 — 종합

받은 리포트를 합쳐 **사용자에게 하나의 그림**으로 낸다. 에이전트 리포트를 그대로 이어붙이지 않는다.

```
## 요청 범위
- 걸린 축: ...
- 걸린 저장소: ...

## 현재 동작
- (파일 경로 근거)

## 영향 범위
| 저장소 | 대상 | 변경 필요 | 근거 |

## 호환성
- 호환 | 비호환(승인 필요) | 확인 필요

## 확인 필요
- (에이전트들이 `확인 불가`로 표시한 것 통합. 중복 제거)
```

## 4단계 — 계획 · 승인

`.claude/rules/git-safety.md`의 **Plan Mode 우선 목록**(멀티모듈·보안·Kafka/Outbox·트랜잭션·Proto·Schema·CI/CD·대규모 리팩터링)에 걸리면 — 이 스킬을 쓸 정도의 요청은 대개 걸린다 — **수정 전에 계획을 먼저 제시하고 승인을 받는다.**

- 비호환 계약 변경은 구현 전 승인이 필수다.
- 저장소가 여러 개면 **저장소별 변경과 배포 순서**를 계획에 넣는다(예: proto 변경 → backend 배포 → frontend 배포).
- 계획은 최소 변경 기준으로 낸다. 요청 범위 밖 리팩터링을 끼워넣지 않는다.

## 5단계 — 실행 (메인이 순차로)

**코드 수정은 서브에이전트에 위임하지 않고 메인에서 한다.** 이유: 변경 의도와 승인 범위가 메인 컨텍스트에만 있고, 여러 저장소에 걸친 수정은 순서가 결과를 바꾼다.

저장소별 작업 규칙:
- **backend**: main에서 브랜치를 파고 작업 → 커밋
- **frontend / infra**: main에서 작업 → 커밋
- 각 저장소의 `CLAUDE.md`·`.claude/rules/`를 그 저장소 파일을 건드리기 전에 읽는다.

## 6단계 — 병렬 검증

바꾼 저장소마다 검증 에이전트를 **동시에** 부른다.

| 저장소 | 에이전트 | 범위 |
|---|---|---|
| backend | `build-runner` | 좁은 범위부터. `<service>Ci`는 필요할 때만, `serviceCi`(전체)는 승인 필요 |
| backend | `arch-reviewer` | 헥사고날·Outbox·트랜잭션·Redis Key 규약 |
| frontend | `frontend-verifier` | `npm run build`(타입 체크 포함) + `npm run lint` |
| infra | `deploy-auditor` | 배포 스크립트 정적 분석. **스크립트 실행 금지 = 실행이 곧 배포** |

여러 backend 서비스를 바꿨으면 `build-runner`도 서비스별로 나눠 병렬 호출한다.

## 7단계 — 보고 · 커밋

루트 `CLAUDE.md`의 완료 보고 형식(`변경 요약 / 검증 / 영향 범위 / 남은 사항`)을 따른다. 실행하지 못한 검증은 사유와 함께 밝힌다.

커밋은 저장소마다 따로, 각 저장소의 커밋 규칙을 따른다(backend는 `.claude/rules/commit-pr.md`의 `[<type>] <scope>: <subject>`).

## 하지 않을 것

- 에이전트를 순차로 하나씩 호출하기 — 병렬 이점이 사라진다
- 한 에이전트에 모듈·저장소를 몰아 넣기 — 컨텍스트 격리 이점이 사라진다
- 에이전트에게 코드 수정 위임 — 승인 범위가 흐려진다
- 에이전트 리포트 원문을 사용자에게 그대로 전달 — 종합이 이 스킬의 존재 이유다
