# 커밋 · PR 메시지 규칙

이 파일은 커밋/PR 메시지를 작성할 때 읽는다. squash 머지는 **PR 제목을 커밋 subject 로 쓰고 `(#PR)` 을 붙인다**(`.claude/hooks/auto-pr.sh`) → 관리 대상은 **제목**, **PR 본문**, 그리고 **커밋 트레일러**다.

## 제목 (커밋 제목 = PR 제목)

형식: `[<type>] <scope>: <subject>`

### type (브래킷 안)

| type | 용도 |
|---|---|
| `feat` | 새 기능·능력 추가 |
| `fix` | 버그·오류 수정(머지 직후 긴급 후속 수정 포함) |
| `refactor` | 동작 변화 없는 구조/네이밍 정리 |
| `perf` | 처리량·지연·자원 사용을 바꾸는 변경. 외부 동작은 그대로다 — 구조를 바꿔도 목적이 성능이면 `refactor` 가 아니라 이쪽이고, PR 본문에 **무엇이 얼마나 바뀌었는지 근거 수치**를 적는다 |
| `docs` | 문서만 변경 |
| `test` | 테스트만 변경 |
| `chore` | 빌드/의존성/설정 등 잡무 |
| `ci` | GitHub Actions workflow |
| `cd` | 배포 스크립트/파이프라인 |

### scope

- 모듈/영역 **디렉터리명**을 쓴다. **여러 모듈·전역 변경이면 생략**한다.
- 축약 별칭(가독성): `config` = spring-cloud-config, `eureka` = spring-cloud-eureka-server, `gateway` = spring-cloud-api-gateway.
- 그 외는 디렉터리명 그대로: `chat`, `market`, `user`, `notification`, `oauth2-client`, `oauth2-authorization-server`, `websocket-gateway`, `market-detection`, `outbox`, `common`, `git-config-repo`, `docker`, `build` …

### subject

- 한국어, **명사형 종결**("정리/추가/수정"), 마침표 없음, 50자 내외.
- 예:
  - `[docs] config: 모듈 문서 추가`
  - `[refactor] chat: 트랜잭션 경계 정리`
  - `[fix] market: database 추가`
  - `[refactor] 의존성 정리` (전역 → scope 생략)

## 커밋 본문

- 상세는 PR 본문에 쓰고 커밋 본문은 짧게 유지한다. 브랜치 커밋 메시지는 **머지 커밋 본문에 그대로 남을 수 있다** — 그 커밋 하나가 무엇을 왜 바꿨는지에 한정해 쓴다.
- 단, **AI가 작성한 커밋**은 본문 끝에 실제 작업에 사용된 AI 제품의 공동 저작 트레일러를 넣는다. 특정 제품을 프로젝트 기본값으로 가정하지 않는다.
  ```text
  # Codex로 작성한 경우
  Co-authored-by: Codex <noreply@openai.com>

  # Claude Code로 작성한 경우
  Co-authored-by: Claude <noreply@anthropic.com>
  ```
  **모델명이나 모델 버전은 넣지 않고 제품명만 쓴다.** 모델은 계속 바뀌므로 실제 작성 주체와 어긋날 수 있다. 어느 모델 버전을 썼는지가 아니라 **사람이 단독 저작하지 않았다는 사실과 실제 사용한 AI 제품**이 기록 대상이다.
  이 트레일러는 squash 머지 후에도 유지된다(`auto-pr.sh`가 브랜치 커밋에서 수집해 머지 커밋 본문에 넣는다). 사람이 단독 작성한 커밋에는 넣지 않는다.
  **도구 기본값이 모델명을 넣으므로 커밋 전에 트레일러를 직접 확인한다.** 이 규칙과 어긋나는 과거 이력은 재작성하지 않는다(→ `git-safety.md`, 현황은 `TODO.md` 4.15).

## PR 본문 (고정 템플릿)

이 템플릿이 **PR 본문의 단일 정본**이다. 초안 작성은 `pr-draft` skill로 하되, 형식은 여기를 따른다.

```markdown
## 배경
왜 바꾸는지 1~2줄

## 변경
- 핵심 변경 bullet

## 검증
- 실행/결과, 또는 '문서만 변경(코드 변경 없음)'

## 참고사항
- 의도적으로 하지 않은 것(범위 밖으로 남긴 것)
- 그 밖에 리뷰어(=미래의 나)가 알아야 할 특이사항

### 트레이드오프   ← 아래 "쓰는 기준"에 해당할 때만. 아니면 이 소절을 통째로 뺀다
| 결정 | 택한 것 | 포기한 것 | 탈락 후보 · 이유 |
|---|---|---|---|
| (무엇을 정했나) | (고른 안) | (그 대가로 잃은 것) | (검토했으나 안 고른 안 — 왜) |
```

### 길이 (중요)

- **본문 전체 30줄 내외.** 넘으면 무엇을 뺄지 먼저 판단한다. 리뷰어는 diff를 같이 본다 — 본문은 diff가 답하지 못하는 것(왜·트레이드오프·안 한 것)만 담는다.
- 본문에 쓰지 않는다: 파일별 수정 내역 나열(diff가 보여준다), 코드·설정 값 인용(파일에 있다), 이 PR 범위 밖 후속 계획, 규칙 문서 내용 재설명.
- 커밋이 여러 개면 `## 변경`은 **커밋당 한 줄**을 기본으로 한다.
- 아주 작은 변경은 각 섹션 한 줄로 축약 가능. `## 참고사항`은 없으면 생략한다(나머지 3절은 필수).
- **`## 참고사항`의 항목은 체크리스트지 고정 소제목이 아니다.** 해당 없는 항목은 빼고, 있는 것만 적는다. **칸을 채우려고 쓰지 않는다.**
- **외부 계약을 바꿨으면 `## 참고사항`에 반드시 적는다**(생략 불가 — `external-contracts.md`의 계약 목록 기준). 최소 항목: 하위 호환 여부, 영향받는 소비처(프론트·다른 서비스·인프라), 배포 순서. 계약 문서(`docs/ARCHITECTURE.md` §6–7 등)를 갱신했으면 그 사실도 적는다.
- **길이를 줄일 때 트레이드오프 표를 먼저 자르지 않는다.** diff로 복원할 수 없는 유일한 정보다. 먼저 자를 것은 변경 내역 나열이다.

### 트레이드오프 표 — 쓰는 기준

**아래 중 하나라도 해당하면 쓴다.**
- 되돌리기 비용이 큰 선택(구조·계층·외부 계약·의존성·정책·데이터 모델)
- 실제로 후보를 둘 이상 검토한 선택
- 성능·정합성·복잡도·안전성 중 하나를 다른 것과 맞바꾼 선택

**하나도 해당하지 않으면 소절을 통째로 뺀다.** 아래는 쓰지 않는 예다.
- 오타·오기 수정, 문서 문구 정리
- 정답이 하나뿐인 버그 수정
- 기계적 변경(포맷, 이름 일괄 변경, 의존성 버전 업)
- 규칙·문서가 이미 정해놓은 대로만 따른 변경

**표를 만들려고 후보를 지어내지 않는다.** 실제로 검토하지 않은 안을 "탈락 후보"에 적는 것은 허위다. 후보가 하나였으면 트레이드오프가 아니라 그냥 구현이다.

각 행은 한 줄로 쓴다. 결정이 3개를 넘으면 PR을 쪼갤 신호다.
- `## 검증`에는 실행하지 못한 항목과 사유도 함께 적는다(→ `git-safety.md` 테스트·검증 무결성).
- PR 본문에는 AI 저작 푸터를 넣지 않는다. AI 저작 표시는 **커밋 `Co-authored-by:` 트레일러**로만 남긴다(위 "커밋 본문" 참고). 제목에도 AI 표시를 넣지 않는다(사람 커밋과 동일한 형식 유지).
