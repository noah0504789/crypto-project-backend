# ADR-003: chat 실시간 경로의 용량 목표와 커넥션 예산

- 상태: 채택됨
- 범위: chat 메시지 실시간 경로(websocket-gateway STOMP 팬아웃, chat outbox 기록)와 MySQL 커넥션 배분

## 한 줄 요약

**같은 방에서 사람이 늘면 보낼 메시지가 제곱으로 는다.** 이 ADR 은 그 구조에서 ① 사람 수에 비례해 커지던 낭비를 코드에서 걷어내고 ② 남은 값(DB 커넥션·큐 크기)을 어떤 근거로 잡았는지 적는다. **"몇 명까지 되는가"는 아직 답하지 못한다** — 측정 장비가 부족해서다.

## 용어

| 말 | 뜻 |
|---|---|
| **팬아웃** | 한 명이 보낸 메시지를 방에 있는 모두에게 복사해서 보내는 것 |
| **접속자 `N`** | 지금 방에 붙어서 메시지를 주고받는 사람 수 |
| **방 멤버** | 방에 속한 사람 전체. 접속 안 한 사람도 포함된다 |
| **프레임** | 소켓으로 실제로 나가는 전송 단위. 메시지 여러 개를 한 프레임에 담을 수 있다 |

## 이 문서가 정하는 것

목표는 **용량 숫자를 확정하는 게 아니다.** 두 가지다.

1. **사람 수에 비례해 커지던 비용을 코드에서 없앤다.** 이건 끝났고 근거는 실제 측정값이다(§1).
2. **남은 값(커넥션·큐)은 계산으로 정하고 측정으로 확인한다.** 계산에 쓴 목표치는 아직 가정이라 운영 장비에서 다시 재면 바뀐다(§2·§3).

**정하지 못한 것: 이 시스템이 몇 TPS 까지 버티는가.** 측정을 16GB 맥 한 대에서 돌리는데 회차마다 스왑이 10GB 넘게 발생한다. 접속자를 더 올리면 **서버가 아니라 맥이 먼저 죽어서** 그 뒤 숫자는 서버 한계라고 말할 수 없다. 그래서 여기 수치는 "여기까지 버틴다"가 아니라 **"여기까지는 막히는 데가 없더라"** 는 뜻이다.

## 어떤 조건에서 잰 숫자인가

여기 나오는 값은 전부 **아래 한 조건에서 나왔다.** 조건이 다르면 비교가 안 된다.

| 항목 | 값 | 왜 이렇게 잡았나 |
|---|---|---|
| 방 | 1개, 멤버 **302명** | 접속자보다 멤버가 많은 게 현실이다. 이 차이가 있어야 "멤버 수에 비례하는 비용"이 드러난다. 멤버 2명으로 재던 때는 §1 표의 아래 두 줄이 안 보였다 |
| 동시 접속 | **100명** (한 명당 계정 1개, 계정 300개 발급) | 계정을 나눠 쓰면 한 계정에 세션이 여러 개 붙어 ACK·뱃지가 그 수만큼 뻥튀기된다. 실제 사용자는 계정당 세션 1개다 |
| 전송 | 한 명이 60건, 1초 간격 | 사람당 초당 1건 |
| 시간 | 60초 동안 계속 보내고, 끝난 뒤 60초 더 받음 | 짧게 몰아치는 게 아니라 지속 부하. 남은 걸 다 받아봐야 유실을 셀 수 있다 |
| 장비 | 16GB 맥 1대에 컨테이너 23개 | 측정 전용 장비가 아니다. 상한을 못 재는 이유가 여기 있다 |

**축이 두 개라는 걸 기억해야 한다.**

- **접속자 수** → 팬아웃을 정한다. 보낼 건수가 제곱으로 는다.
- **방 멤버 수** → 접속 여부와 상관없이 **쓰기 비용**을 정한다(멤버십 갱신, outbox 행 크기).

둘을 같이 올리면 어느 쪽이 원인인지 못 가린다. 그래서 **멤버는 302로 고정하고 접속자만 올렸다.**

## 결정 세 가지

각 줄에 **근거가 어디서 왔는지**를 같이 적는다.

- **측정** — 서버가 직접 센 값
- **계산** — 식으로 구한 값
- **가정** — 목표로 정해둔 값. 실제로 확인한 게 아니다

| # | 결정 | 근거 |
|---|---|---|
| 1 | 용량은 **접속자 수**로 말하고, 근거는 서버가 직접 센 값만 쓴다. 응답 시간은 근거로 안 쓴다 | **측정** — 접속 100명에서 유실 0 · 거절 0 을 3회 재현. 상한은 못 쟀다 |
| 2 | DB 커넥션은 서비스마다 따로 늘리지 않고 **DB 서버 하나에 쓸 수 있는 총량**을 정해 나눈다 | **계산** + **측정으로 확인**(커넥션 대기 0) |
| 3 | 큐 크기는 **허용 지연을 구간마다 나눠서** 정한다 | **가정**(지연 10초) 위의 **계산**. 측정으로 확인한 건 큐가 거의 안 쌓였다는 것뿐 |

## 1. 무엇을 걷어냈나 [측정]

**아래는 한계치가 아니라 통과한 지점이다.** 위 조건에서 세 번 돌렸고 세 번 다 같은 결과가 나왔다. 이 구간에서는 **서버 어디에도 밀린 곳이 없다.**

| 지표 | 결과 |
|---|---|
| 메시지 유실 | **0** (받은 수 = 보낸 수 × 접속자 수, 세 회차 정확히 일치) |
| ACK 실패 | **0** |
| STOMP 큐에서 버린 작업 | **0** |
| STOMP 큐에 쌓인 깊이 | 최대 0~2 |
| DB 커넥션 대기 | 0 (고치기 전에는 대기 92 · 풀 고갈 예외 24건) |

### 보낼 건수는 여전히 제곱이다

```
접속자 100명이 각자 초당 1건을 보내면
  들어오는 건수 = 100건/초
  나가는 건수   = 100건 × 받는 사람 100명 = 10,000건/초
```

**배칭을 넣어도 이 10,000건은 그대로다.** 다만 그게 **몇 번의 전송으로 나가는지**는 달라진다. 100ms 안에 들어온 메시지를 봉투 하나에 담으면, 브로커가 사람 수만큼 복사하는 건 똑같지만 복사할 **대상 개수**가 줄어든다.

```
                       배칭 전        배칭 후 (창당 30건으로 묶였다면)
brokerChannel 작업     100/초          3/초
소켓 전송(프레임)      10,000/초       300/초        ← 같은 ×100 확장, 대상이 줄었다
실제 전달 메시지       10,000/초       10,000/초     ← 그대로
```

**소켓으로 나가는 횟수는 줄고, 사람들이 받는 메시지 수는 그대로다.** 프레임 하나에 여러 건이 실리기 때문이다(실측 24~34건). 즉 줄어든 것은 건수가 아니라 **전달 1건당 드는 비용**이다.

| 걷어낸 것 | 무엇에 비례해 커지던 비용인가 |
|---|---|
| 메시지를 방 단위로 묶어 보내기(PR #265) | 프레임 수 — 지금은 프레임 하나에 24~34건이 실린다 |
| 뱃지를 방 단위로 합치기(PR #263) | 메시지마다 **멤버 수**만큼 작업이 생기던 것 |
| ACK 를 브로커 채널 밖으로(PR #267) | 한 계정에 붙은 **세션 수**만큼 뻥튀기되던 것 |
| 뱃지를 브로커 채널 밖으로(PR #282) | 사용자 목적지 변환이 만들던 **1+N개의 broker 작업** |
| 멤버 점수 갱신을 한 번에(PR #270) | MongoDB 왕복이 **방 멤버 수**만큼 반복되던 것 |
| 이벤트에서 멤버 목록 빼기(PR #271) | outbox 한 줄 크기가 **방 멤버 수**에 비례하던 것 |
| ParallelGC 지정(인프라) | 컨테이너 메모리가 1,792MB 미만이면 JVM 이 SerialGC 를 골라 GC 가 초 단위로 멈추던 것 |

위 셋은 **접속자 수**, 아래 둘은 **방 멤버 수**에 걸려 있던 비용이다. 멤버가 2명이던 예전 측정에서는 아래 둘이 아예 안 보였다.

여기서 멈춘 이유는 서버가 아니라 장비다(→ 위 「이 문서가 정하는 것」, `TODO.md` 5.12).

### 예전에 쓰던 공식은 버렸다

처음에는 이렇게 계산했다.

```
M = 같은 방에서 동시에 말하는 사람 수
r = 한 사람이 초당 보내는 건수
C = 서버가 초당 소화할 수 있는 전달 건수

보낼 건수 = M × r × M = M² × r
버티려면   M² × r ≤ C   →   M ≤ √(C/r)

당시 값 C ≈ 6,000, r = 1  →  M ≤ 약 77명
```

**틀렸다.** `C` 를 고정된 값으로 봤는데 고정이 아니었다. 처리량이 "초당 바이트"가 아니라 **"초당 프레임"** 에 걸려 있어서(1차 측정 JFR: 278바이트 쓰는 데 209ms), 메시지를 묶어 보내자 `C` 자체가 올라갔다. 예측은 77명이었는데 **실제로는 100명에서도 유실이 0** 이었다.

식을 지우지 않고 남겨둔 이유는 **틀린 지점이 쓸모 있어서**다. `C` 를 상수로 두면 "사람 수를 줄이는" 쪽만 보게 되는데, 자릿수를 바꾼 건 `C` 를 올린 배칭이었다. 용량은 계산이 아니라 **재현된 측정값**으로 말한다.

### 처리량을 늘리는 다른 방법은 왜 안 골랐나

보낼 건수는 제곱으로 늘고 처리 능력은 잘해야 비례해서 는다. 그래서 **보낼 것을 줄이는 쪽부터** 했다.

| 후보 | 무엇을 하는 건가 | 판단 |
|---|---|---|
| **메시지 묶어 보내기** | 여러 건을 한 프레임에 담아 전송 횟수를 줄인다 | **채택**(PR #265). 프론트가 받는 형식이 바뀌는 외부 계약 변경이라 함께 고쳤다 |
| 가상 스레드 | 기다리는 시간을 회수해 동시 처리량을 늘린다 | 보류. Java 21 로 올려야 하고 전 서비스에 영향이다. 게다가 **효과가 없을 수도 있다** — 막히는 구간이 `synchronized` 안이면 가상 스레드도 똑같이 묶인다. 착수 전 `-Djdk.tracePinnedThreads=full` 로 확인이 먼저다 |
| 서버 대수 늘리기 | 세션을 나눠 서버당 전송량을 줄인다 | 효과는 있지만 근본은 아니다. 컨슈머 그룹이 서버마다 달라서 **받는 쪽 부하는 오히려 는다** |

## 2. DB 커넥션 예산 [계산 + 측정으로 확인]

커넥션은 **DB 서버가 가진 자원**이다. 서비스마다 필요하다고 늘리면 서버가 감당 못 한다. 그래서 서버별로 총량을 정하고 그 안에서 나눈다.

MySQL 은 쓰기용(master)·읽기용(replica) 2대다. 서버 하나가 받을 수 있는 접속이 기본 151개인데, 관리·복제·모니터링 몫으로 16개를 남겨 **앱이 쓸 수 있는 건 서버당 135개**로 본다.

**쓰기 서버(master)**

| 서비스 | 최대 | 비고 |
|---|---:|---|
| chat | **30** | 최소=최대라 30개를 계속 물고 있다 |
| notification | 15 | 〃 |
| market | 10 | |
| user | 10 | |
| outbox-poller | 10 | |
| **합계** | **75** | 예산 135 안 |

**읽기 서버(replica)**: market 10개가 전부다. 읽기 전용 연결을 만드는 서비스가 market 하나뿐이다. 설정 파일에 읽기 항목이 있어도 코드에서 만들지 않으면 연결은 생기지 않는다. **읽기 쪽 숫자를 쓰기 예산에 더하지 않는다.**

### 몇 개가 필요한지는 "얼마나 오래 붙잡는가"가 정한다

```
필요한 커넥션 = 초당 트랜잭션 수 × 한 건이 커넥션을 붙잡는 시간
```

chat 목표를 초당 300건으로 **가정**하면(실제로 도달한 값이 아니다), 필요한 커넥션 수는 **붙잡는 시간에 그대로 비례**한다. 0.05초면 15개, 0.5초면 150개다.

그래서 **풀을 키우는 대신 붙잡는 시간을 줄였다.** 메시지 저장 로직이 트랜잭션 안에서 MongoDB 를 한 번 다녀오는데, 예전에는 트랜잭션이 시작되는 순간 MySQL 커넥션을 잡고 **그 MongoDB 왕복 내내 들고 있었다.** 실제로 한 건이 5.139초를 붙잡았고, 커넥션을 못 받아 실패한 게 360건, 그 때문에 브로드캐스트 10.06%가 사라졌다(PR #257).

`LazyConnectionDataSourceProxy` 를 붙여 **첫 SQL 을 실행할 때** 커넥션을 잡도록 미뤘다. 최신 측정에서 커넥션 대기는 0이다.

- **풀을 키우는 건 답이 아니었다.** 서버 예산이 무너지고, 붙잡는 시간은 그대로라 부하가 늘면 같은 벽에 다시 부딪힌다.
- **트랜잭션은 그대로 둔다.** outbox 3줄(저장·브로드캐스트·뱃지)이 한 덩어리로 성공하거나 실패해야 한다. 쪼개면 사용자에겐 보이는데 저장은 안 된 메시지가 생기고 되돌릴 방법이 없다.
- 같은 문제가 남은 서비스 점검은 `TODO.md` 4.7.

## 3. 큐 크기 [가정 위의 계산]

메시지가 도착하기까지 **10초까지는 봐준다**고 두고(합의된 목표가 아니라 후보다), 그 10초를 구간마다 나눠 큐 크기를 정했다. 아래 초당 건수도 계산에 쓴 가정이다.

| 구간 | 허용 지연 | 큐 크기 |
|---|---:|---|
| 받기 → 저장 → Kafka → 브로커 | 5초 | inbound 600, broker 3,000 |
| 소켓으로 내보내기 대기 | 5초 | outbound 30,000 |

**broker 큐와 outbound 큐는 세는 대상이 다르다.** broker 는 복사되기 **전** 메시지를, outbound 는 복사된 **후** 전송을 센다. 그래서 크기 차이가 크다. outbound 30,000개는 한 건 1KB 로 잡아 약 30MB 이고 게이트웨이 힙(512MB) 안에 들어온다.

**큐를 키우는 건 처리량을 사는 게 아니라 기다릴 시간을 사는 것이다.** 처리 능력이 그대로면 큐를 늘려도 더 오래 기다릴 뿐이다.

## 지켜야 할 것

- **버릴 때 기본 정책(`AbortPolicy`)을 쓰지 않는다.** 그 정책은 거절할 때마다 예외 메시지를 만들면서 `ThreadPoolExecutor.toString()` 을 호출하고, 그 안에서 풀 전체 락을 잡는다. 정상 제출은 이 락을 안 쓰고 **거절 경로만** 쓰기 때문에, 거절이 몰리면 제출하는 쪽이 전부 이 락에서 줄을 서고 느려진 제출이 큐를 더 밀어 거절을 늘린다. 1차 측정 JFR 30초에서 **락 대기 3,637건 중 3,613건이 이 경로**였다. 그래서 예외 대신 카운터만 올린다.
- **ACK 풀만 버리지 않는다.** ACK 는 버리면 보낸 사람이 결과를 영영 모른다. 대신 큐가 차면 호출한 스레드가 직접 실행한다(`CallerRunsPolicy`). 그래도 되는 이유는 **ACK 발생량이 사람 수에 비례**할 뿐이기 때문이다 — 팬아웃처럼 제곱으로 늘지 않아 밀리는 구간이 길지 않다.
- **큐가 가득 차면 전송 작업을 버리고 숫자만 남긴다.** 무엇이 버려졌는지는 `stomp.executor.rejected{pool,kind}` 의 `kind` 로 갈라 본다 — 브로드캐스트 1건은 방 전원이 못 받고, ACK 1건은 보낸 사람이 결과를 영영 모르고, 뱃지는 다음 차례가 덮어쓴다. 브로드캐스트는 재시도·DLQ 가 없다.
- **ACK 와 뱃지는 브로커 채널을 지나지 않는다.** 세션과 목적지별 구독 정보를 직접 찾아 소켓 채널로 바로 보낸다. 과거 사용자 목적지 경로는 최초 broker 1회, 세션별 재큐잉 N회, outbound N회로 **1+2N개의 채널 작업**이 필요했다. 직접 발송은 broker 항을 0으로 만들고 outbound N회만 남긴다. 세션·구독을 찾지 못하거나 전송하지 못하면 폴백하지 않고 `chat.message.ack.direct.failed`·`chat.badge.direct.failed` 로 센다.
- **실행기·풀·묶는 시간 설정은 `git-config-repo/dynamic/` 에 있지만 busrefresh 로 안 바뀐다.** 풀은 기동할 때 만들어지고 이 프로젝트는 `@RefreshScope` 를 쓰지 않는다. 값을 바꾸려면 **재배포**해야 한다.
- **들어오는 입구에서 미리 거절하는 건 운영 장비로 옮긴 뒤에 넣는다**(→ `TODO.md` 5.14). 얼마나 밀리면 거절할지는 실제 측정에서 나오는데, 지금 장비 숫자로 정하면 운영에서 다시 재야 한다.

## 아직 모르는 것

- **몇 TPS 까지 버티는지, 몇 명까지 되는지.** 못 쟀다(이유는 위). **이 문서의 어떤 숫자도 "여기까지 버틴다"는 뜻이 아니다.** 재려면 측정 장비 분리가 먼저다(→ `TODO.md` 5.12).
- **다음에 어디가 먼저 막히는지.** 지금은 큐도 거의 안 쌓이고 커넥션도 안 기다려서, 다음 병목이 뭘지 데이터로 말할 수 없다.
- **응답 시간의 절대값.** 같은 조건 3회에서 p90 이 4.95초~14.5초로 흔들리고 그 편차가 맥의 스왑량과 같이 움직인다. 실제 응답 시간은 운영 장비에서 다시 잰다.
- **클라이언트가 유실을 알아채는 방법.** 지금은 없다. 버리는 쪽을 택한 이유는 "다시 조회하면 복구되니까"가 아니라 **"피크에 전원을 느리게 만드는 것보다 일부를 버리는 게 낫다"** 는 판단이다. 메시지에 방별 순번이 없어서 빠진 걸 감지할 수단 자체가 없다(→ `TODO.md` 5.5, 순번 설계는 5.3-b).
