# Chat WebSocket Gateway 부하테스트 결과

## 테스트 도구와 환경

- 부하 생성 도구로 k6를 사용했다.
- k6의 WebSocket API로 API Gateway의 Native WebSocket endpoint에 연결하고, STOMP CONNECT·SUBSCRIBE·SEND frame을 직접 전송했다.
- ACK 응답·지연과 방 Broadcast 도착·지연·미도달·중복을 k6 custom metric으로 수집했다. 당시 스크립트는 성공 ACK와 거절 ACK를 구분하지 않았다.
- k6 부하 발생기는 별도 클라우드 환경에서 실행해 테스트 서버의 CPU·Memory를 부하 생성 작업과 경쟁시키지 않았다.
- 클라우드 부하 발생기와 테스트 서버 사이의 외부 네트워크를 거쳤으므로 왕복 지연·지터·대역폭 등 네트워크 오버헤드가 측정값에 포함됐다.
- 16GB RAM 장비 한 대에 인프라, 모니터링, 서비스 컨테이너를 함께 실행했다.
- 부하 생성 중 모든 컨테이너가 같은 장비의 CPU·Memory·Network I/O를 경합해 장비 자체에도 많은 지연이 발생했다.

## 테스트 조건

- **Native WebSocket `/ws-native`로 연결.** 프론트엔드가 사용하는 경로와 같다.
  게이트웨이는 SockJS(`/ws`)도 열어두지만 **이번 측정에는 포함하지 않았다** — 아래 수치는 전부 Native 경로 결과다.
- 모든 VU가 같은 채팅방을 구독
- VU당 메시지 10개를 1초 간격으로 `/msg/chat.send`에 전송
- 방의 모든 구독자가 모든 메시지를 받으므로 이론상 Broadcast 수는 `VU² × 10`
- 130·150·200명 각각을 WebSocket Gateway 1대·2대 구성에서 실행(총 6회, 구성당 1회)
- 인증 계정은 2개를 VU가 번갈아 사용

원본 실행 로그는 `raw/`, 측정 당시 관측 화면은 `grafana/`, 대시보드 정의는 `dashboards/`에 보존했다.
대시보드 JSON은 측정 데이터가 아니라 조회 화면 정의이므로 아래 수치는 k6 원본 로그를 기준으로 정리했다.

중복 Broadcast는 모든 실행에서 0건이었다.

각 컬럼은 k6가 실제로 센 값이다.

- **ACK 응답률(10초 내)**: 전송 후 10초 안에 ACK 프레임을 받은 비율. 서버가 성공(`success=true`)으로 응답했는지 거절(`success=false`)로 응답했는지는 **구분하지 않는다.** 당시 스크립트가 두 경우를 함께 셌다.
- **Broadcast 수신률**: 기대 `VU² × 10` 중 실제로 도착한 비율(= 10초 내 도착 + 지연 도착).
- **미도달**: 기대치에서 도착분을 뺀 값. **"영구 유실"이 아니라 "수집 창이 닫힐 때까지 안 온 것"**이다. 스크립트는 마지막 전송 후 30초(Native 기준)만 더 받고 연결을 끊으므로, 그 뒤에 도착했을 메시지는 전부 미도달로 잡힌다. 여기에는 ① 서버가 거절해 발행되지 않은 것, ② 발행됐지만 창이 닫힌 뒤 도착한 것, ③ 전달 도중 실제 유실이 섞여 있고 로그만으로는 나눌 수 없다.

ACK 응답률과 미도달의 관계는 다음과 같다. gRPC `chat-client` deadline이 10초이고(`git-config-repo/dynamic/websocket-gateway.yml`)
스크립트의 ACK 대기도 10초라, 저장이 deadline을 넘겨 거절된 경우 **거절 ACK는 스크립트가 이미 무응답으로 처리한 뒤에 도착한다.**
따라서 거절이 ACK 응답률을 부풀렸을 가능성은 낮고 대부분 무응답 쪽으로 계산됐다고 본다(코드·설정 기준 추정, 로그로 확정 불가).

또 200 VU·WS 2대에서 ACK 무응답은 998건인데 끝까지 도착하지 않은 메시지는 307건이다.
**무응답의 대부분은 저장 실패가 아니라 ACK 지연**이며, 그 메시지들은 늦게라도 저장·발행됐다.

### WebSocket Gateway 스케일아웃 비교

| VU | ACK 응답률 변화 | 10초 내 Broadcast 변화 | Broadcast avg 변화 | Broadcast p95 변화 | 미도달 변화 |
|---:|---:|---:|---:|---:|---:|
| 130 | -27.00%p | -9.24%p | 7.15% 감소 | 49.96% 증가 | 변화 없음 |
| 150 | +34.40%p | +14.66%p | 44.14% 감소 | 41.15% 감소 | 26.05% → 0.00% |
| 200 | -4.00%p | +16.99%p | 52.87% 감소 | 47.07% 감소 | 5.44% → 15.35% |

**Broadcast latency는 실제 도착한 메시지만 집계하고 미도달분은 제외한다.** 따라서 평균·p95 감소만으로
전체 성능이 개선됐다고 판단하지 않고 **ACK 응답률, 10초 내 도착률과 미도달률을 함께 봐야 한다.**

## 결과 해석

- **무너진 것은 유실이 아니라 지연이다:** 6회 중 3회는 미도달이 0건이다. 130명·WS 2대 실행은 ACK를 10초 안에 못 받은 것이 351건인데도 Broadcast는 169,000건이 전부 도착했다. **응답이 늦은 것이지 버려진 것이 아니다.**
- **부하 구조:** 모든 사용자가 같은 방에서 초당 1개를 보내기 때문에 Inbound는 사용자 수에 비례하지만 **Broadcast는 `사용자 수²`으로 증폭된다.** 130명만 접속해도 **초당 최대 16,900건의 전달 작업**이 발생한다.
- **130명 — 지연 관측:** 미도달과 중복은 0건이었다. 보낸 메시지가 전부 발행돼 전원에게 도달했다는 뜻이므로 이 두 실행에는 **서버 거절이 없었다.** 다만 **10초 기준을 넘긴 Broadcast가 14.03%(WS 1대)~23.28%(WS 2대)**였다. 이 수치의 허용 여부는 **서비스 SLO를 정한 뒤 판단**해야 한다.
- **150명 — 불안정성 증가:** **10초 내 Broadcast가 11.78%(WS 1대)~26.44%(WS 2대)**로 떨어졌고 WS 1대 실행에서는 **26.05%가 미도달**했다. WS 2대 실행은 미도달 0건이라 거절이 없었다. 각 조건을 1회씩만 측정했으므로 두 실행 차이는 구성 차이와 실행 편차가 섞인 값이다.
- **200명 — 심한 성능 저하:** **ACK 응답률이 두 실행 모두 약 50%**로, 절반은 10초 안에 어떤 응답도 받지 못했다. Broadcast 평균 지연은 **최대 41.68초**, 미도달은 **최대 15.35%**였다. WS 2대 실행의 미도달 61,400건은 VU 수로 정확히 나눠떨어진다(307 × 200). **특정 메시지 307개를 전 VU가 똑같이 못 받았다**는 뜻이며, 세션마다 다르게 빠지는 부분 전달 실패와는 형태가 다르다. 원인은 두 가지가 모두 가능하고 로그로는 구분되지 않는다 — ① 그 메시지들이 발행되지 않음(gRPC deadline 초과 후 `hardDelete` 보상 삭제 등), ② 발행은 됐지만 **수집 창이 끝난 뒤 도착**해 집계되지 않음.
- **스케일아웃 효과:** WS Gateway를 1개에서 2개로 늘렸을 때 **150·200명에서 Broadcast 평균/p95가 41~53% 감소**해 지연은 개선됐다. 반면 **ACK 응답률과 미도달은 함께 좋아지지 않았다.** 늘린 것은 팬아웃을 담당하는 게이트웨이뿐이고
  **저장을 담당하는 chat은 6회 내내 1대**였다(`raw/` 파일명의 `chat1`). 게다가 모든 컨테이너가 같은 16GB 장비를 나눠 쓰므로
  게이트웨이를 하나 더 띄우면 다른 컨테이너의 자원이 줄어든다. **순수한 수평 확장 실험이 아니었다.**
- **현재 결론:** **150·200명 구간에서는 명확한 성능 저하**가 나타났다. **130명의 허용 여부와 정확한 안정 한계는 SLO 및 130명 미만의 추가 측정 없이는 확정할 수 없다.**
- **다음 검증:** **50·80·100·120명 구간을 추가 측정**해 ACK 응답률, Broadcast p95와 미도달률이 허용 범위에 머무는 경계를 찾아야 한다. 재측정 시에는 성공 ACK와 거절 ACK를 분리 집계하는 현재 스크립트를 사용한다.

### 서버 지표로 본 원인 (150 VU · Chat 1대 · WS Gateway 1대)

측정 당시 Grafana 화면을 `grafana/`에 보존했다. 세션 패널이 단일 게이트웨이 인스턴스에서 150까지 오르는 것으로
150 VU·WS 1대 실행임을 식별했다.

| [`grafana/150vu-chat1-ws1-errors-resource.png`](grafana/150vu-chat1-ws1-errors-resource.png) | gRPC 오류 카운터, executor max, 세션 수, 게이트웨이 CPU, chat GC·heap |
| [`grafana/150vu-chat1-ws1-gateway-gc.png`](grafana/150vu-chat1-ws1-gateway-gc.png) | 게이트웨이 heap promotion rate, GC action/cause |

관측값은 다음과 같다.

- **gRPC 저장 실패가 0건이다.** `ws_grpc_client_errors_total{method="save"}`와 `{method="hardDelete"}` 모두 구간 내내 0이다.
  **이 실행에서 서버 거절은 없었다.** 앞 절에서 "거절인지 지연인지 로그로는 못 가른다"고 한 부분이 이 화면으로 해소된다 —
  적어도 이 실행의 미도달 26.05%는 거절이 아니다.
- **자원은 남았다.** 게이트웨이 `process_cpu_usage`가 최대 **0.2(20%)**, chat heap 사용률 22~34%, chat GC pause는 0에 수렴한다.
  HikariCP pending도 0이다. **CPU·메모리·커넥션 어느 것도 고갈되지 않았다.**
- **그런데 STOMP executor 스레드는 상한까지 찼다.** pool max는 inbound 32 / broker 64 / outbound 96이고,
  활성 스레드가 각각 그 값 근처(32 / 63 / 95)까지 올라간다. CPU가 20%인데 스레드가 상한이라는 것은
  **스레드가 계산이 아니라 대기 상태였다**는 뜻이다(전송 대기 추정, 확인 필요).
- **채널 처리량에 상한이 보인다.** 채널 RPS가 최대 6,000/s 부근에서 꺾인다.
  이 조건이 요구하는 팬아웃은 초당 150 × 150 = **22,500건**이다. 요구량이 처리량을 크게 웃돌면 큐가 아니라 시간축으로 밀린다.
  총 225,000건을 관측된 처리량으로 소화하면 수십 초가 걸리며, 이는 실측 Broadcast p95 42.45초와 같은 자릿수다.
- **chat gRPC 저장 지연은 0.4초 → 1.5초로 올랐다.** 저장 경로도 느려지긴 했지만 초 단위이고,
  Broadcast 지연(수십 초)과는 규모가 다르다. **병목은 저장이 아니라 팬아웃 쪽이다.**
- **게이트웨이 GC는 잦아졌지만 멈추지는 않았다.** minor GC(Allocation Failure)가 5 → 42.5로 뛰고
  promotion rate가 급증하지만 pause time은 0에 가깝다. 할당 압력은 커졌어도 GC가 지연의 원인은 아니다.

정리하면 **자원 고갈도 저장 실패도 아니고, 팬아웃 전송 처리량이 요구량을 못 따라간 것**이다.
`사용자 수²` 증폭을 그대로 받아내는 구조가 한계였다는 뜻이며, WS Gateway를 2대로 늘렸을 때
같은 구간의 Broadcast 지연이 41~53% 줄어든 실측과도 방향이 일치한다.

### 이 결과로 말할 수 있는 것과 없는 것

| 항목 | 판단 |
|---|---|
| Broadcast 지연(avg·p95)과 10초 내 도착률 | **그대로 사용 가능.** 도착한 메시지만 집계하는 지표라 집계 한계와 무관하다 |
| 부하 증가에 따른 저하 경향 | **그대로 사용 가능.** 130 → 150 → 200에서 일관되게 악화됐다 |
| 스케일아웃의 지연 개선 효과 | **그대로 사용 가능.** 150·200명 구간에서 avg·p95가 41~53% 감소했다 |
| 130명 두 건과 150명 WS 2대의 ACK·미도달 | **그대로 사용 가능.** 미도달 0건이라 거절이 없었음이 확정된다 |
| 150명 WS 1대의 미도달 | **거절 아님이 확인됐다.** gRPC 저장 실패 0건. 지연 또는 수집 창 종료로 설명된다 |
| 200명 두 건의 ACK·미도달 | **분해 불가.** 해당 실행의 서버 화면이 없다 |
| 서버 처리 실패율 자체 | **150 VU·WS 1대 실행은 0건으로 확인됐다**(`ws_grpc_client_errors_total`). 나머지 5개 실행은 화면이 없어 미확인 |
| 병목의 위치 | **자원 고갈이 아니라 팬아웃 처리량이다**(150 VU·WS 1대 기준). 나머지 5개 실행은 서버 화면이 없어 미확인 |
| ACK 무응답의 의미 | **저장 실패가 아니다.** 200 VU·WS 2대 기준 무응답 998건 대 미도달 307건으로, 대부분은 10초를 넘긴 ACK 지연이다 |

### 환경 제약과 신뢰 범위

- **환경 제약:** 16GB RAM 장비 한 대에 인프라·모니터링·서비스 컨테이너를 모두 실행해 CPU·Memory·Network I/O 경합과 호스트 지연이 함께 발생했다.
- **부하 발생기 분리:** k6는 클라우드에서 실행해 부하 생성에 필요한 CPU·Memory가 16GB 테스트 서버의 경쟁 비용에 들어가지 않았다. 서버와 부하 발생기를 분리한 점은 측정 환경의 장점이다.
- **ACK 팬아웃 증폭:** 계정 2개를 모든 VU가 공유해 ACK 한 건이 그 사용자의 모든 세션(약 `VU / 2`)에 복제됐다. 150명·WS 1대 실행의 `ws_msgs_received` 279,033건은 Broadcast 166,383 + ACK 112,500(=1,500 × 75) + CONNECTED 150으로 정확히 설명된다. 즉 수신 메시지의 약 40%가 계정 공유로 생긴 ACK 증폭분이다. 스크립트는 자기 `clientMessageId`만 집계하므로 위 표의 수치는 왜곡되지 않지만, 서버가 실제로 내보낸 메시지 양은 실사용 조건보다 크다.
- **네트워크 오버헤드:** 외부 네트워크 구간의 왕복 지연·지터·대역폭 영향이 ACK와 Broadcast latency에 포함됐다. 측정값은 서버 내부 처리시간이 아니라 외부 클라이언트가 체감하는 End-to-End 시간이다.
- **절대값 해석:** 측정값에는 애플리케이션 처리 한계, 호스트 자원 한계와 외부 네트워크 비용이 함께 섞여 있으므로 독립된 운영 환경의 정확한 최대 처리량으로 사용할 수는 없다.
- **일관된 경향:** 같은 도구와 시나리오에서 부하가 증가할수록 ACK 응답률 저하, Broadcast 지연과 미도달 증가가 반복됐다. 따라서 결과가 무의미하거나 오차가 지나치게 큰 것은 아니다.
- **스케일아웃 효과:** WS Gateway를 1개에서 2개로 늘린 구성에서 150·200명 구간의 Broadcast 지연이 개선돼 수평 확장의 상대적 효과를 확인했다.
- **테스트의 의의:** 정확한 최대 TPS를 확정하는 자료보다는 병목이 나타나는 구간을 찾고, 구성 변경과 스케일아웃의 상대적 효과를 비교하는 기준선으로 의미가 있다.
